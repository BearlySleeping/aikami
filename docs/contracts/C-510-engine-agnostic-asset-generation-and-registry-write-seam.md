## User Outcome

After this contract, a developer or an agent can run one engine-agnostic command — `bun run --cwd apps/backend/image generate:asset prop "rusty iron gate"` — and get a catalog-ready asset (bytes + tag + category + `generated:<engine>` provenance) without writing transport code, and a player-facing generated image (avatar, expression, scene) can be persisted into the local asset registry and resolved by the running game through the same code path.

## Success Measures

- **Time/latency target**: recipe resolution + engine dispatch begins submitting within 100 ms of the CLI's first statement (measured after Bun process start, which is ~50–100 ms on its own and is not part of the budget); the shared client keeps the existing poll cadence; no synchronous work on first paint.
- **Offline/degraded behavior**: generation targets a local engine only (`127.0.0.1` by default) and `registerGenerated` is a local OPFS + Turso write. Neither requires network or sign-in.
- **Production journey enabled**: a player or developer creates an asset with a local engine and the game renders it via a registry tag; the same generated asset can be handed to the existing catalog publish pipeline unchanged.

## Overview

Today generation and storage are two disconnected halves: assets are content-addressed, provenance-aware, and resolvable, but nothing writes generated bytes into them; and every engine repeats its own HTTP protocol. This contract introduces one portable `GenerationEngineClient` (sd.cpp first, ComfyUI second) in `@aikami/local-ai`, a declarative recipe registry mapping a catalog category to an engine and parameters, a `generate:asset` CLI that uses both, and a `registerGenerated` write seam that persists generated bytes into the local registry + cache with `generated:<engine>` provenance. It also fixes expression resolution to go through the registry. Audio/video modalities, ComfyUI promotion to default, an MCP front door, and end-user publishing are explicitly deferred.

## Design Reference

- **Engine pattern**: `apps/frontend/client/src/lib/services/image/engine/types.ts` and `image_engine_factory.svelte.ts` (C-388) — narrow interface, one adapter per engine, capability flags, factory selection. Generalize `ImageEngineClient` to `GenerationEngineClient`; do not widen the dialogue/TTS `FrontendAiInterface`. Reuse the existing `ImageEngineId` (`packages/shared/types/src/lib/media/image_engine.ts:11`, `'auto' | 'sdcpp' | 'comfyui'`) rather than declaring a second engine-id union — `GenerationEngineId` is `Exclude<ImageEngineId, 'auto'>`, exactly as `ResolvedImageEngineId` already is.
- **Return-shape bridge**: the existing `ImageEngineClient.generate()` resolves to `ImageGenerationResult` carrying a `Blob` (`types.ts`), while the portable `GenerationResult` carries `Uint8Array` (the Bun CLI has no `Blob`). The frontend adapter owns that conversion (`new Blob([bytes], { type: mimeType })`) so `SdCppEngine`/`ComfyUiEngine` keep their current public shape and C-388's adapter tests keep passing.
- **Portable core**: `packages/shared/local-ai/src/lib/` — plain TS, no Svelte runes, no browser-only globals; already depended on by local-stack. The shared client lives here so the Bun CLI and the browser use one implementation.
- **Registry/cache convention**: `packages/frontend/storage/src/lib/assets.ts` (repository) and `apps/frontend/client/src/lib/services/assets/asset_manager.svelte.ts` (cache + resolve). `put` verifies SHA-256 before caching (`opfs_cache_backend.ts`, `asset_hasher.ts`); `registerGenerated` must keep that invariant.
- **Provenance**: `packages/shared/schemas/src/lib/game/asset_provenance.ts` — `source: "generated:<provider>"` already exists; generated assets must populate it.
- **Catalog output**: `scripts/src/lib/ops/generate_asset_seed.ts` (`AssetSeedRow`) and `scripts/src/lib/catalog/pipeline.ts` — the CLI's staging format must be consumable without hand-editing.
- **Service definitions**: `scripts/src/lib/herdr/session.ts` + `packages/shared/constants/src/lib/dev_services.ts` for the (deferred) audio profile; not modified by this contract. (Engine-profile references for the record: `session.ts:277` `image`, `:341` `image-comfyui`; `apps/backend/local-stack/compose.yaml:121` `image`, `:287` `comfyui`; `apps/backend/local-stack/stack/fetch_models.ts:71`.)

## Architecture Directives

- **One generated-asset descriptor, two sinks.** `GeneratedAsset` is the shared unit. The Bun CLI writes it to catalog staging (files + a manifest fragment); the client writes it to OPFS + the registry. Do not invent two descriptor types.
- **One derivation, `toGeneratedAsset`.** The descriptor is never hand-assembled at a call site. A single shared helper derives it from `(GenerationResult, AssetRecipe, engine)` — computing `sha256` over the bytes, expanding `tagTemplate` against a slug of the prompt, taking `category`/`ext` from the recipe and `provenance.source = \`generated:<engine>\``. Both sinks call it. Without this, AC-4's Given ("a generated image result") has no producer and the CLI and client drift.
- **Slug + tag rules.** `tagTemplate` expands `{{slug}}` to the prompt lowercased with every run of non-`[a-z0-9]` collapsed to `-` and leading/trailing `-` trimmed; the result must satisfy `AssetRefSchema.tag`'s `^[a-z0-9]+(:[a-z0-9_.-]+)+$` or registration fails loudly.
- **Local sources outrank remote ones.** A `local-generated` `asset_sources` row is written at `priority = -1`. `AssetRegistryRepository.listSources` orders by `priority ASC, backend ASC` (`assets.ts:227`), so relying on the alphabetical tiebreak (`'local-generated' < 'r2'`) would be accidental — and would silently turn AC-4's offline guarantee into an R2 fetch the moment a tag also exists in the seed. Pin it explicitly.
- **Generated tags must not collide with seed tags.** `_seedCompactChunk` upserts `assets` with `ON CONFLICT(id) DO UPDATE SET hash = excluded.hash, version = excluded.version` (`assets.ts:558-570`). A generated asset registered under a tag that also appears in the boot seed is silently re-pointed at the remote bytes (and its version bumped) on the next seed pass. `registerGenerated` must reject a tag already present in the seed with a readable error.
- **The shared client is framework-agnostic.** No Svelte runes, no `$state`, no DOM types in `@aikami/local-ai`; the frontend adapter wraps it and owns reactive state.
- **Recipes are data, not code.** Adding a category/engine mapping is a data-file change. A recipe with an unknown engine or an engine that cannot honour a field must fail loudly, never silently drop.
- **Capabilities gate recipes.** Validate every recipe against the resolved engine's capabilities before dispatch; strip or reject unsupported fields explicitly.
- **Fail fast on unknown models.** sd-server queues forever on an unknown model name (`generate_avatar.ts:209`); the shared client must verify the model exists via `listModels()` (or reject a non-listed `--checkpoint`) before submitting.
- **Serialize single-slot engines.** sd-server and ComfyUI each process one job at a time; the shared client serializes requests per engine instance.
- **Do not mutate the shipped engine topology.** No new herdr service, compose profile, or model manifest entry in this contract.

## Quality Requirements

- **Offline/degraded mode**: generation targets a local engine; `registerGenerated` is local-only. No cloud call is introduced on any generation or registration path. `AGENTS.md` boot/offline invariants are preserved.
- **Accessibility/input**: N/A — no new interactive UI in this contract (the CLI is the surface; the expression fix is resolver-internal).
- **Performance budget**: `registerGenerated` writes one OPFS file + one Turso transaction; no full-registry scan. Recipe resolution is a map lookup.
- **Security/privacy**: engine base URLs are loopback by default (`127.0.0.1`); reject non-`http(s)` schemes. Never log full base64 payloads — log byte lengths. The CLI never executes engine-supplied paths.
- **Persistence/migration**: adding the `local-generated` source backend and `registerGenerated` rows must not perturb the existing seed derivation revision (`assets.ts:26-50`, `r4`) or cause re-seed churn; see Migration & Rollback. Concretely: `SEED_DERIVATION_REVISION` must stay at `4` — generated rows are not seed rows, and `seedFingerprint()` digests only the seed document, so a bumped revision would force a pointless re-seed on every install for no data change.
- **Never silently drop a generated asset**: if `scan_assets.ts` cannot classify a staged asset's category it `continue`s without a message (`scan_assets.ts:101-109`). The CLI must fail loudly when its staging output would be skipped, rather than reporting success for an asset that never reaches the catalog.
- **Cancellation/retry/idempotency**: every `generate()` accepts an `AbortSignal` and issues the engine's native cancel; `registerGenerated` is idempotent by `sha256` + `tag` (re-registering the same bytes does not duplicate rows).
- **Observability**: log engine id, resolved recipe, resolved model, and duration at debug; log registration (tag, sha256, sizeBytes) at info. Never log prompt-injected secrets.

## Migration & Rollback

- **Old data compatibility**: existing `assets`/`asset_sources` rows are untouched. Readers that do not know `local-generated` must treat it as an unknown-but-tolerated backend (skip/warn), never crash. The column is free-text `TEXT NOT NULL` (`migrations.ts:199-205`), so an old binary reading a new database already tolerates the value at the SQL layer; the risk is only in TypeScript narrowing — widen the union rather than asserting.
- **Migration**: add the `local-generated` value to the source-backend schema/types. **No SQL migration and no `SEED_DERIVATION_REVISION` bump** — the revision guards the *derivation of seed rows*, and generated rows are not seed rows (`seedFingerprint()` digests the seed document only). Existing generated persona avatars (data URLs in the persona row) are left where they are; a future contract may migrate them, not this one.
- **Compatibility with `_pruneStaleSources`**: that pass deletes every `backend = 'bundled'` row and every row whose URL matches `%firebasestorage.googleapis.com%` (`assets.ts:485-497`). A `local-generated` row with a `local-generated:<sha256>` URL matches neither and survives — but this must be asserted by a test, not assumed, because a future widening of that DELETE would silently wipe every generated asset.
- **Rollback**: remove/ignore `local-generated` rows and cache entries; the feature flag below gates the write path. No destructive migration to reverse. Reverting the code leaves orphaned `local-generated` rows, which old readers tolerate per the compatibility rule above.
- **Feature flag or kill switch**: `PUBLIC_ASSET_GENERATION` (frontend) — when off, `registerGenerated` is a no-op and the existing demo/placeholder path is unchanged; the CLI remains available to developers. Declare it in `apps/frontend/client/src/env.d.ts` alongside `PUBLIC_IMAGE_ENGINE` (`env.d.ts:25`) so it is typed, not `import.meta.env`-splatted.
- **Failure recovery**: registration is atomic per asset (write cache bytes, then insert the registry row; on failure, delete the cache bytes). A crash between the two must not leave a resolvable tag pointing at missing bytes.
- **Tag-collision recovery**: if `registerGenerated` rejects a tag already present in the seed (Architecture Directives), the error must name the tag and the conflicting seed hash so the caller can regenerate under a distinct tag. Regenerating an existing *generated* tag is allowed and bumps the row version rather than overwriting the previous hash silently.

## Scope Boundaries

- **In Scope:**
  - Shared, framework-agnostic `GenerationEngineClient` + `GenerationRequest`/`Result`/`Capabilities` in `@aikami/local-ai`, with `GenerationEngineId` derived from the existing `ImageEngineId`.
  - sd.cpp adapter (moved from the four duplicates) and ComfyUI adapter; frontend `engine/` files delegate to them.
  - Declarative `AssetRecipe` schema + a recipe registry with image recipes (prop, portrait, expression, tileset as data).

## Contract Size & Split Rule

> 📋 Split rules: see [SHARED_SECTIONS.md](SHARED_SECTIONS.md#contract-size--split-rule)

**For this contract:** one outcome — *generated bytes become first-class assets, produced engine-agnostically*. The engine client (authoring plane) and the `registerGenerated` seam (runtime plane) share one data model (`GeneratedAsset` + `AssetProvenance`) and one invariant (content hash = identity). Shipping the shared client alone leaves generation dead-ending at staging; shipping the write seam alone leaves a fourth copy of the protocol feeding it. They are not independently useful, so they stay together. The registry-side work (AC-4, AC-5, AC-8) is not independently mergeable either: a `local-generated` source row with no writer, or a writer with no reader, leaves the repo worse off than before. Deferred phases (audio/video, MCP, publishing, ComfyUI promotion) are named as separate future contracts rather than partially completed here.

## Edge Cases & Gotchas

- **Two sinks, one descriptor**: the Bun CLI cannot write browser OPFS/Turso. The `GeneratedAsset` descriptor is shared; the CLI's sink is catalog staging, the client's sink is OPFS + registry. Do not try to unify the sinks.
- **Tag collision on regeneration**: regenerating the same tag with different bytes (new seed) must bump the registry row version, not silently point old references at new art. Save data references tags — this is the C-442-style trap.
- **Tag collision with the seed** (different from regeneration): a generated tag that also exists in the boot seed is overwritten by `_seedCompactChunk`'s `ON CONFLICT DO UPDATE SET hash = excluded.hash` on the next boot. `registerGenerated` must refuse it up front; the alternative — a generated tag shadowing a catalog tag forever — is a silent art swap.
- **`props` is half-registered today**: `CatalogCategory` has it, `ASSET_CATEGORIES` does not, and `scan_assets.ts` drops unknown categories without a message. Verify the round-trip in a test, not by eye — a silent drop looks exactly like success.
- **Provenance/licence**: generated assets inherit the model's licence; record the model id and engine in provenance so the catalog attribution preflight can gate publication.
- **`local-generated` unknown to old readers**: tolerate, don't crash. The column is free-text, so this is a TypeScript-narrowing concern, not a SQL one.
- **Model hot-swap**: sd-server loads one model at start (no runtime swap); a recipe naming a different model than the loaded one must fail fast against `listModels()`.
- **Large assets**: cap size (`MAX_UPLOAD_SIZE`, `constants/game_assets.ts:328`) and fail fast rather than stalling registration.
- **Expression fallback fabrication**: the current resolver returns a URL for a non-existent file; the fix must not regress existing LPC overlay behavior. The resolver is synchronous — do not convert it to async to reach `assetManager.resolve()`; use `assetStore.resolveUrl`.
- **`blob:` URLs are not durable**: never persist one as an `asset_sources.url`. After a reload it is a dead reference and the tag becomes unresolvable offline.

### Deviations from Spec

1. **`GenerationRequest` gained `sampler` and `denoise`.** The contract's State & Data Models sketch omits both, but `GenerationCapabilities.sampler` is declared and C-388's `ImageGenerationRequest` carries them; without them the C-388 passthrough tests (`sample_method`, `denoise` on the wire) cannot be preserved. Additive only.
2. **Model verification is sd.cpp-only.** The contract's directive names the sd-server "queues forever on an unknown model" problem specifically. ComfyUI already fails fast on an unknown `ckpt_name`, and adding a `listModels()` round trip there would break C-388's checkpoint tests without adding safety.
3. **`PUBLIC_ASSET_GENERATION` is declared in `src/env.ts`, not only `env.d.ts`.** In this repo `$app/env/public` is generated from `src/env.ts` (`defineEnvVars`); the `declare module` block in `env.d.ts` does not merge into it. Both files now declare the flag.
4. **`GenerationRequest.modality` is validated against the adapter's modality** (an audio request to an image engine is refused before any request). The contract's schema has the field but does not state the check; it is the only place a future audio engine could otherwise be mis-dispatched.
5. **Test-harness updates.** `image_engine_factory.test.ts`'s ComfyUI "single implementation" grep test and `sdcpp_engine.test.ts`'s fetch mock were updated because the transport legitimately moved to `@aikami/local-ai` (AC-1's own requirement).
6. **Guard baselines updated.** `asset_manager.svelte.ts` genuinely shrank (815 → 809) so the size ratchet was locked in; three new exported symbols with no in-game production caller yet (`AssetManager.registerGenerated`, `GeneratedAssetRegistrationDeps`/`RegisterGeneratedResult`, `ExpressionRegistrySeam`) were captured in the orphaned-capability baseline with comments. Generating an asset *from inside the game* is a deferred follow-up (MCP front door), so no production caller exists in this contract.
7. **The sd.cpp poll deadline defaults to 900s and is configurable end to end.** Attempt 1 shipped `QUEUE_WAIT_MS = 120_000` with no escape hatch, which timed out the documented AC-2 command on real hardware. `DEFAULT_SDCPP_POLL_DEADLINE_MS` is now 900_000 (the pre-C-510 `generate:avatar` default), threaded through `AssetGenerationOptions.queueWaitMs` → `createGenerationEngine` → `SdCppGenerationEngineOptions.queueWaitMs`, exposed as `generate:asset --timeout <seconds>` (default 900), and passed explicitly by the frontend `SdCppEngine` so the in-game path keeps its pre-C-510 budget. The timeout error now names the elapsed time and the deadline used. Covered by three new local-ai tests, one new `runAssetGeneration` forwarding test, and two new CLI tests.
8. **No screenshot / `ai_validate_image` evidence.** This session exposes no `browser` or `ai_validate_image` tool, and the contract's own Quality Requirements state there is no new interactive UI (the CLI is the surface; the expression fix is resolver-internal). The production-path evidence is instead: a live `generate:asset` run against the real sd-server, the live `image_service.test.ts` integration run, and a production-factory wiring test for the resolver. AC-5's "production smoke" is therefore covered at the composition-root level, not through a rendered route.
8. **`validate()` could not run.** Its affected-project detection fails with `Parse failed: Invalid project record at index 1` on moon's project-record shape — reproducible with no changes staged (it failed identically before and after this work), so it is a tool/environment issue, not a consequence of this change. The equivalent gates were run per project instead: `biome check` (clean), `local-ai`/`schemas`/`types`/`constants`/`frontend-storage`/`client` typecheck (clean), `client:build` (clean), `local-ai` (198) / `frontend-storage` (69) / `client` (2930) / `image` (8) tests, and all 10 `scripts:guard` tasks.
