## Problem & Baseline Evidence

- **Current behavior**: When a player interacts with an NPC (`NPC_INTERACTED` bridge event), the dialogue overlay opens with a static action context menu (`dialoguePhase === 'MENU'`). Five hardcoded verb buttons are displayed: Persuasion, Intimidation, Stealth, Attack, Custom. The player must choose a verb BEFORE the LLM ever sees their intent. This breaks immersion — the player's first interaction with an NPC is a mechanical menu, not a natural-language exchange. The LLM only learns what the player intends AFTER the dice roll, which wastes its ability to evaluate context and determine whether a roll is even appropriate.

- **Reproduction**:
  1. Start the game (`/game`) in emulator mode.
  2. Approach an NPC and press Enter.
  3. Observe: the dialogue overlay shows five static verb buttons (Persuasion, Intimidation, Stealth, Attack, Custom). There is no free text input until "Custom" is explicitly selected.
  4. Select "Persuasion" — a DC is set, dice roll, LLM gets the result. The LLM never had a chance to say "this doesn't need a roll."
  5. Open the dev sandbox at `/dev/sandbox/dialogue` — same static menu.

- **Known gaps**:
  1. The action menu (`ACTION_OPTIONS`) is a hardcoded `static readonly` array in `DialogueOverlayViewModel` — no dynamic derivation from NPC/player state.
  2. There is no intent-analysis phase before the dice roll — the system assumes every interaction needs a roll.
  3. The LLM never receives the player's raw natural-language input before the mechanical resolution.
  4. Choice buttons (`activeChoices`) come from the LLM's `choices[]` in the turn envelope, but they are generic (`Ask X more`, `Leave`) rather than contextual.
  5. No concept of "suggestion chips" with intent tags — choices are plain text labels with optional commands.

## User Outcome

After this contract, a player can walk up to any NPC, type whatever they want in natural language (e.g. "I'm the health inspector, let me through"), and the AI GM will dynamically determine whether a skill check is needed, what DC to set, and what contextual follow-up options to offer — all without seeing a single pre-canned verb button.

## Success Measures

- **Time/latency target**: Call #1 (intent analysis) under 2s p95; Call #2 (roll resolution) under 2s p95. Combined turn time under 4s + dice animation.
- **Offline/degraded behavior**: When AI is unavailable, dialogue falls back to authored content pack branches (existing C-328 fallback). Chips are derived from authored dialogue keys instead of LLM output.
- **Production journey enabled**: Player engages with NPCs through natural language from the first interaction — no mechanical menu gate.

## Overview

Refactors the NPC dialogue interaction from a static verb-button menu (BG3-style) to a free-text-first model with AI-driven intent analysis and contextual suggestion chips. The player types natural language immediately; a two-call LLM pipeline first determines whether a mechanical roll is needed (and if so, what DC and stat modifier apply), then resolves the outcome with narrative and dynamically generated follow-up chips. State ownership stays in code — the LLM proposes deltas, the game validates and applies them. The existing command dispatch system, authored fallback, and content pack integration are preserved.

## Design Reference

- **Existing orchestrator pattern**: `NpcDialogueService` in `npc_dialogue_service.svelte.ts` — injected `NpcDialogueContentProvider`, `NpcDialogueTextGenerator`, `NpcDialogueExecutors`. Keep the same constructor injection pattern.
- **Existing dialogue command schema**: `NpcDialogueAiEnvelopeSchema` in `npc_dialogue_command.ts` — discriminated union, `additionalProperties: false`, `Value.Check` validation. Extend with new envelope types following same pattern.
- **Existing ViewModel pattern**: `DialogueOverlayViewModel` extends `BaseViewModel`, uses `$state` for phases, delegates to `npcDialogueService`. Keep MVVM boundary.
- **Existing dice flow**: `declared → awaiting_click → rolling → revealed` phases in `skillCheckState`. Reuse for the post-intent-analysis dice flow.

## State & Data Models

### Intent Analysis — Call #1 Input

```typescript
// packages/shared/schemas/src/lib/game/npc_dialogue_command.ts

/** Context projection for intent analysis — sent to LLM call #1. */
export type NpcIntentAnalysisInput = {
  /** The player's raw natural-language input. */
  player_input: string;
  /** NPC identity and disposition. */
  npc_context: {
    name: string;
    persona: string;
    /** Allowed command kinds for this NPC. */
    allowed_commands: NpcDialogueCommandKind[];
  };
  /** Player character sheet summary (stats, level, class). */
  player_context: {
    character_sheet_summary: string;
    level: number;
    class_id: string;
  };
  /** Recent conversation turns (player + NPC, newest last). */
  recent_history: Array<{ role: 'player' | 'npc'; content: string }>;
  /** Read-only world facts (active quests, flags). */
  game_state_facts: string[];
};
```

### Intent Analysis — Call #1 Output

```typescript
/** LLM output from call #1 — determines if a mechanical roll is needed. */
export type NpcIntentAnalysisOutput = {
  /** Whether this player action requires a skill check / dice roll. */
  requires_roll: boolean;
  /** The skill to check against (e.g. "Deception", "Persuasion"). Only set when requires_roll is true. */
  check_type: string | null;
  /** Difficulty class (5–20). Only set when requires_roll is true. */
  difficulty_class: number | null;
  /** Which player stat modifier applies (e.g. "CHA", "STR"). Only set when requires_roll is true. */
  modifier_source: string | null;
  /** Short narrative that plays BEFORE any roll UI appears — the NPC's reaction to what was said. */
  narrative_pre_roll: string;
  /** Suggested follow-up chips for this turn (0–4). */
  suggested_chips: NpcSuggestionChip[];
};
```

### Suggestion Chip

```typescript
/** One contextual suggestion chip rendered below NPC messages. */
export type NpcSuggestionChip = {
  /** Unique chip ID within this turn. */
  id: string;
  /** Display label (e.g. "Ask about the stolen gems", "Intimidate"). */
  label: string;
  /** Semantic intent tag — drives UI treatment (icons, urgency). */
  intent_type: 'dialogue' | 'skill_check' | 'combat' | 'trade' | 'quest';
  /** Pre-filled text sent as the next player message when tapped. */
  prefill_text: string;
};
```

### Roll Resolution — Call #2 Input

```typescript
/** Sent to LLM call #2 — the outcome of the dice roll. */
export type NpcRollResolutionInput = {
  /** The skill that was checked. */
  check_type: string;
  /** The difficulty class the GM set. */
  difficulty_class: number;
  /** The total roll (d20 + modifier). */
  roll_total: number;
  /** Whether the roll passed the DC. */
  outcome: 'pass' | 'fail';
  /** The player's original text (for context). */
  player_input: string;
};
```

### Roll Resolution — Call #2 Output

```typescript
/** LLM output from call #2 — narrative resolution + state change proposals. */
export type NpcRollResolutionOutput = {
  /** The NPC's narrative response incorporating the roll outcome. */
  narrative_result: string;
  /** State changes the LLM proposes. Game validates and applies each. */
  state_deltas: NpcStateDelta[];
  /** Updated contextual chips for the next player turn (0–4). */
  suggested_chips: NpcSuggestionChip[];
};
```

### State Delta (LLM Proposes, Game Applies)

```typescript
/** A single state change proposed by the LLM. Game validates before applying. */
export type NpcStateDelta = {
  /** What kind of state change this is. */
  kind: 'trust_change' | 'flag_set' | 'flag_clear' | 'inventory_grant' | 'inventory_remove' | 'relationship_update';
  /** Target entity (NPC ID, player ID, item ID). */
  target: string;
  /** Numeric value when applicable (trust delta, quantity). */
  value?: number;
  /** String value when applicable (flag name, relationship label). */
  label?: string;
};
```

## Quality Requirements

- **Offline/degraded mode**: When AI is unavailable, fall back to authored content pack dialogue with derived chips (C-328 existing path). Chips are generated from available authored dialogue keys + NPC capabilities. No soft-lock.
- **Accessibility/input**: Free-text input uses existing `<AutoResizeTextarea>` with keyboard nav (Enter to send, Escape to end). Chips are focusable buttons with arrow-key navigation. All chip intent types have aria-labels.
- **Performance budget**: Call #1 under 2s p95. Call #2 under 2s p95. Dice animation ~1.5s (existing). Total turn latency under 4s + animation. No per-frame work in the dialogue overlay.
- **Security/privacy**: LLM output is untrusted input — all schemas use `additionalProperties: false` and `Value.Check` before dispatch (existing pattern). State deltas are validated against a whitelist before application. The LLM never mutates state directly.
- **Persistence/migration**: Dialogue history messages are ephemeral (not persisted across reload). No save format changes. Existing IndexedDB draft store (`draftStore`) continues to work for input text recovery.
- **Cancellation/retry/idempotency**: Existing AbortController pattern (`_activeAbortController`) covers both calls. `markCommandExecuted` / `wasCommandExecuted` guards continue to prevent double-dispatch. Call #2 is only reachable after call #1 completes — cancel during call #1 prevents dice phase entirely.
- **Observability**: Existing `this.debug()`/`this.warn()` logging in `NpcDialogueService` extended to cover both calls (`_analyzeIntent:start`, `_analyzeIntent:requires-roll`, `_resolveRoll:complete`). Token counts and latency logged per call.

## Migration & Rollback

If this contract changes persistent state (schemas, save format, routing, providers):

- **Old data compatibility**: N/A — dialogue history is ephemeral. No persisted state structure changes.
- **Migration**: N/A — no data migration needed.
- **Rollback**: The new `NpcIntentAnalysisOutputSchema` and `NpcRollResolutionOutputSchema` are additive to the existing schemas file. No existing schemas are removed. The `NpcDialogueAiEnvelopeSchema` stays for backward compatibility during transition. The ViewModel can be rolled back by restoring the `dialoguePhase === 'MENU'` branch and `ACTION_OPTIONS`.
- **Feature flag or kill switch**: Add a `useFreeTextFirst` flag in `npcDialogueService.configure()` (default `true`). Setting to `false` restores the legacy action menu path.
- **Failure recovery**: If call #1 fails, fall through to authored fallback (existing `_buildAuthoredTurn` path). If call #2 fails, render the `narrative_pre_roll` from call #1 as the final message and offer generic chips (`Ask more` / `Leave`).

### AC-5: State Deltas — LLM Proposes, Game Validates and Applies

**Given** call #2 (roll resolution) or call #1 (if no roll) returns `state_deltas[]`
**When** the game processes the LLM response
**Then** each delta is validated against a whitelist before application: `trust_change` must be in [-10, +10], `flag_set`/`flag_clear` must reference known flag names, `inventory_grant`/`inventory_remove` must reference items in the content pack. ## Edge Cases & Gotchas

- **Empty input**: Sending empty text must be a no-op (existing guard in `sendMessage()`)
- **Rapid successive inputs**: The `_activeAbortController` concurrency gate must cancel any in-flight call #1 or #2 before starting a new one
- **LLM returns invalid schema**: Existing `Value.Check` + repair pattern in `_parseEnvelope()` extended to new envelope types. On repeated failure, fall back to authored.
- **Chip tap during streaming**: Chips must be disabled while `isStreaming` or `isResolvingSkillCheck` is true
- **LLM sets DC outside 5–20 range**: Schema-enforced at validation (`Type.Integer({ minimum: 5, maximum: 20 })`). Out-of-range values rejected.
- **State delta targets nonexistent flag**: Silently dropped + logged. Must not throw.
- **Feature flag off**: When `useFreeTextFirst: false`, the legacy action menu must render identically to pre-refactor behavior.

## Open Questions

Must be resolved before status becomes `approved`:

- **Q1**: Should the stat-to-skill modifier mapping (currently hardcoded `SkillStatMap` in the ViewModel) move to a content-pack-driven or config-driven source, or is the hardcoded map acceptable for v1?
- **Q2**: How aggressive should the LLM be in requiring rolls? Should there be a "roll threshold" (e.g., only require roll when player intent clearly maps to a skill check) or should the LLM be conservative (require roll for anything non-trivial)?
- **Q3**: Should the two-call pipeline use the same model/endpoint for both calls, or a smaller/faster model for call #1 (intent classification is simpler than narrative generation)?
- **Q4**: Should suggestion chips include a "reroll" cost limit (e.g., max 3 skill-check chips per conversation to prevent fishing)?
- **Q5**: When `requires_roll: false`, should the `narrative_pre_roll` from call #1 be the final output, or should there still be a second lightweight call for chip generation?
- **Q6**: The current system has an address mode toggle (Scene/GM). Does the free-text-first model need address mode, or does the LLM's intent analysis make it redundant?
