- **Migrate `client` and `hub` off the deprecated `kit.alias` vite option to Node subpath imports (`#foo`).** SvelteKit 3 (`chore/sveltekit3-migration`) prints `The \`config.alias\` option is deprecated ...     **Why this is bigger than a find/replace:** Node's `imports` field (the replacement mechanism) _requires every key to start with `#`_ — that's a hard Node spec rule, not a SvelteKit choice. So the `$foo` style aliases map cleanly (`$lib` → `#lib`), but the `@aikami/frontend/theme`-style aliases are a problem: those are **not** real npm/workspace package names (the real workspace package is `@aikami/frontend-theme` with a dash, declared in `dependencies`/`workspace:*` — the vite alias fakes a slash-namespaced name that bypasses the package's own `main`/`exports` and points straight at its `src/`, presumably to skip a build step). `#`-prefixed subpath imports can't preserve that exact `@aikami/...` spelling. Pick one before starting:
    - **(a) Minimal-risk:** keep pointing straight at `src/` (same behavior as today, no build step needed) but rename the alias key to also start with `#`, e.g. `@aikami/frontend/theme` → `#aikami/frontend/theme`. Purely mechanical, same blast radius as the `$foo` renames, but changes the on-screen import style (loses the "looks like a real npm package" convention documented in `.pi/skills`).
    - **(b) Correct-but-bigger:** make each of these a real subpath export of its actual workspace package (add `"exports"` to e.g. `packages/frontend/theme/package.json`, keep consuming it as `@aikami/frontend-theme` or add an `exports` subpath so `@aikami/frontend-theme/...` works), and drop the vite alias entirely for that entry. No `#` needed since it's then a real package specifier, not a subpath import. Requires checking every aliased package's `package.json` for `main`/`exports`/`types` and whether Bun can resolve straight to `.ts` (it usually can, no build step required) before deleting the alias.

- **Tauri desktop can't install the OPFS sqlite3_vfs** — this is a persistence rollout task, explicitly **not a blank-canvas fix**; see the [Tauri boot handoff distinction](guides/TAURI_BOOT_HANDOFF.md#3-ruled-out--do-not-re-investigate). Every boot logs `Ignoring inability to install OPFS sqlite3_vfs: Cannot install OPFS: Missing SharedArrayBuffer and/or Atomics. The server must emit the COOP/COEP response headers...`, and `WasmStorageAdapter` falls back to an in-memory DB snapshotted to IndexedDB instead of true OPFS persistence. Root cause: `apps/frontend/client/src-tauri/tauri.conf.json`'s `app.security.headers` is `{}` — Tauri v2 does support setting `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` there (it's a real, documented config option, not a Rust-side custom-protocol change), which is the missing piece for `SharedArrayBuffer`/`Atomics`. Not flipped yet because COEP `require-corp` requires every cross-origin subresource the app fetches (R2 assets from `assets.bearlysleeping.com`, the hub's `internal_logging` endpoint, any provider API calls) to carry a `Cross-Origin-Resource-Policy` header or be fetched in CORS mode with `Access-Control-Allow-Origin` — an untested, cross-cutting change that could silently break asset/texture loading (which we just fixed) if any of those responses don't already qualify. Needs a dedicated pass: flip the headers, rebuild, and exercise every network path (game asset R2 fetches, internal_logging, all configured AI providers) before merging.
