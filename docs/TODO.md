- The way we create worktree in contract pipeline is not using herdr built in worktree, consider refactoring to use https://github.com/herdrdev/herdr/blob/master/.pi/extensions/herdr-worktree/index.ts, also have herdr worktree extension outside pipeline workflow
- Tauri updater artifact signing is disabled (`bundle.createUpdaterArtifacts: false` in `apps/frontend/client/src-tauri/tauri.conf.json`) to avoid needing `TAURI_SIGNING_PRIVATE_KEY` for local builds while pre-launch. Re-enable once we have real users and a stable release cadence — CI (`release.yml`) already has the signing secrets wired up, so it's a one-line flip back to `true`.
- `bun herdr:start tauri` (`scripts/src/lib/herdr/session.ts`) launches the Tauri desktop binary correctly on Windows (process runs, confirmed via `Get-Process`), but the app's own stdout — `println!` startup logs and the webview console forwarded via `tauri_console_log.ts` — never reaches the herdr pane's captured output, even though it works fine when the same binary is launched directly (not through a herdr pane) with output redirected to a file. Root cause is almost certainly Windows-specific: Tauri release builds are linked as a GUI-subsystem PE binary (`IMAGE_SUBSYSTEM_WINDOWS_GUI`), which doesn't reliably inherit a parent console/pty the way console-subsystem processes do — herdr's ConPTY implementation likely doesn't handle that case. Linux (ELF) and macOS (Mach-O) have no such subsystem distinction at the loader level, so this is expected to be Windows-only — needs verification on Linux/NixOS to confirm `herdr:start tauri` output capture actually works there. If it does, this note only needs updating to say "Windows-only, tracked upstream/not fixable here"; if it doesn't, the bug is somewhere else (worth reopening the investigation).
