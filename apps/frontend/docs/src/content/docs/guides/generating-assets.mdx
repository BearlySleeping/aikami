---
title: Generating Assets Locally
description: One engine-agnostic command that turns a prompt into a catalog-ready asset, a durable batch front door for briefs, and how generated bytes become first-class registry assets the game can render.
---

Aikami can generate art with a local engine — no cloud call, no sign-in. The
C-510 pipeline gives you **one command** for it and, for in-game generation,
one write path that makes the result a real registry asset rather than an
in-memory blob.

## One command

```bash
bun run --cwd apps/backend/image generate:asset prop "rusty iron gate"
```

The invocation is `--cwd`-scoped on purpose: the script is declared in
`apps/backend/image/package.json`, so the bare root form
(`bun run generate:asset …`) fails with `Script not found`.

You name a **recipe**, not an engine. The recipe decides the engine, the
prompt template, the negative prompt and the output category:

| Recipe | Category | Output | Tag |
|---|---|---|---|
| `prop` | `props` | `.png` | `props:<slug>` |
| `portrait` | `portraits` | `.png` | `portraits:<slug>` |
| `expression` | `portraits` | `.png` | `portraits:<slug>` |
| `tileset` | `tilesets` | `.png` | `tilesets:<slug>.png` |
| `music` | `music` | `.wav` | `music:exploration:<slug>` |
| `sfx` | `sfx` | `.wav` | `sfx:<slug>` |
| `ambient` | `ambient` | `.wav` | `ambient:<slug>` |

The **Output** column is what the engine actually returns, not an aspiration.
Everything sd-server produces today is PNG, so the portrait and expression
recipes declare `.png`. The CLI sniffs the returned bytes and refuses a payload
whose declared `Content-Type`, recipe extension and actual container disagree —
WebP output only arrives when a real transformation ships (C-520); bytes are
never relabelled.

Useful flags: `--engine sdcpp|comfyui|ace-step`, `--seed`, `--steps`, `--cfg`,
`--width`, `--height`, `--model`, `--negative`, `--timeout <seconds>`,
`--out`, plus the audio flags below. The slug is the prompt lowercased with
every run of non-alphanumerics collapsed to `-`.

sd-server runs on CPU, so a 512×512/20-step job takes roughly two minutes on a
developer machine and longer under load. `--timeout` is the poll deadline and
defaults to 900s — lower it for a quick smoke test
(`--timeout 120 --steps 4 --width 256 --height 256`), raise it on slow
hardware. A run that hits the deadline exits non-zero and names the deadline it
used.

## Music and sound effects

Audio uses the same command and the same descriptor. The engine is
[ACE-Step](https://github.com/ace-step/ACE-Step) — a local text-to-audio model
(Apache-2.0) — served by its own REST API on `:8094`.

```bash
bun run --cwd apps/backend/image generate:asset music "calm forest loop"
bun run --cwd apps/backend/image generate:asset sfx "metal gate slam" --duration 3
bun run --cwd apps/backend/image generate:asset ambient "rain on a tin roof"
```

The `audio` profile is **opt-in and CUDA-only** — a multi-gigabyte Python
engine is never started unasked:

```bash
# one-time: fetch the checkpoint (~8 GB) and start the engine
COMPOSE_PROFILES=text,image,voice,audio bun run --cwd apps/backend/local-stack up
bun run herdr:start audio          # or start it through herdr
```

Audio flags: `--duration <seconds>`, `--tags <text>`, `--lyrics <text>`,
`--bpm <n>`, `--key <text>`, `--instrumental` / `--no-instrumental`,
`--audio-url`, `--audio-checkpoint`, `--audio-output-dir` and
`--audio-output-mount`.

The audio `--tags` value is **appended** to the compiled recipe prompt, never
substituted for it, so your subject always reaches the engine. A blank or
whitespace `--tags` falls back to the compiled template.

`--bpm` and `--key` are **requested hints, not guaranteed conditioning**.
ACE-Step v1 has no native tempo or key control, so the values are carried as
text in the prompt and the run reports them as `requestedBpm`/`effectiveBpm`
and `requestedKey`/`effectiveKey`. The CLI never prints a bare `bpm`/`key` and
never a `measured*` value no engine reported — a measured field appears only
when an engine genuinely measures its own output.

ACE-Step writes the WAV on **its own** filesystem and returns the path, so the
CLI reads it back through the shared models mount. Set `MODELS_PATH` to your
models bind mount (see the local-stack `compose.models-path.yaml` override), or
pass `--audio-output-mount <dir>`. Without either, the CLI refuses to run and
says why.

A generated track resolves in the game through the existing audio resolver:
the `music` recipe's tag carries an `exploration` segment, so
`resolveBgmUrl('explore')` finds it; `sfx` and `ambient` tags match by slug.
Playback, crossfade and track selection are unchanged (C-249 owns those).

## What it writes

Into `apps/backend/image/src/output/generated/` (gitignored scratch space):

- the image bytes at their catalog-relative path (`props/rusty-iron-gate.png`),
- `manifest.json` — an `AssetManifest` fragment,
- `hashes.json` — an `AssetHashesFile` fragment (SHA-256 + size),
- `generated_asset.json` — the descriptor, with
  `provenance.source = "generated:<engine>"`,
- `generation_audit.json` — the request audit: the compiled subject and tags,
  what the engine actually submitted, and any measured values. Requested,
  effective and measured parameters are distinct fields, so an echoed request
  is never mistaken for a measurement.

Repeated runs merge into the existing fragments, so the directory is a
staging area the [catalog publish pipeline](./publishing-catalog-assets.md)
consumes without hand-editing. The CLI exits non-zero on any engine failure
and refuses to report success for an asset whose category the scanner cannot
classify.

## Batch generation

A single asset is one command; a *brief* is a batch. `generate:batch` turns an
authored brief (`docs/plans/emberwatch_asset_brief.json` is the production
instance) into bounded, resumable jobs with a durable run record, a
cross-process resource lease and namespaced staging.

```bash
# 1. Plan only — strict brief validation, reference/provider resolution and a
#    machine-readable job plan. No engine call, no model download, no write.
bun run --cwd apps/backend/image generate:batch \
  --manifest docs/plans/emberwatch_asset_brief.json --phase slice --plan

# 2. Run the plan's dispatchable items (the phase defaults to the brief's).
bun run --cwd apps/backend/image generate:batch --manifest <brief.json> --run

# 3. Inspect, resume and cancel a run by id.
bun run --cwd apps/backend/image generate:batch --manifest <brief.json> --status <runId>
bun run --cwd apps/backend/image generate:batch --manifest <brief.json> --resume <runId>
bun run --cwd apps/backend/image generate:batch --manifest <brief.json> --cancel <runId>
```

Modes — exactly one, and `--plan` is the default: `--plan`, `--run`,
`--resume <runId>`, `--status <runId>`, `--cancel <runId>`. `--plan` prints the
plan JSON (both phase counts, every item, every structured blocker) and exits
with the blocked-plan code when anything is refused.

Options:

| Flag | Effect |
|---|---|
| `--manifest <path>` | The authored brief; validated strictly before any side effect. |
| `--phase slice\|expansion` | Brief phase to plan or run (default: the brief's `execution.defaultPhase`). |
| `--runs-dir <dir>` | Run-record/staging root (default `apps/backend/image/src/output/runs`). |
| `--out <dir>` | The one-job CLI's staging root, read **only** by `--import-legacy` (default `apps/backend/image/src/output/generated`). |
| `--import-legacy` | Read pre-existing staging through the explicit validated opt-in: read-only, nothing moved, rewritten or swept. |
| `--item <id>` | Restrict a run to one brief item id. |
| `--variation <n>` | Explicit new variation for `--item`: bumps attempt and seed and consumes candidate budget. |
| `--provider <profileId>` | Force a provider profile instead of the brief's preference group. |
| `--request-key <key>` | Client request key for `--item`: the idempotency handle, so a repeated submission resolves to one job. |
| `--run-id <id>` | Explicit run id (default `<briefId>--<phase>`). |
| `--reconcile <itemId>=<provider-completed\|provider-cancelled\|no-provider-work>` | Resolve a `reconciliation_required` job before dispatching (used with `--run`). |
| `--root <dir>` | Root brief reference locators resolve against (default: the repository root). |
| `--engine-url <url>` | Engine base URL override (defaults: the local-stack image profile, or the audio profile for ACE-Step). |
| `--workflow-profile <id>` | Pin the ComfyUI image graph to a versioned workflow profile (`sdxl-legacy`, `flux2-klein-4b-comfyui`) instead of the engine's legacy graph. The compiled graph is validated against the installed node schema before submission; an unavailable node class, an uninstalled weight or a LoRA the profile does not allow fails before the request leaves the process. |
| `--preparation-profile <id>` | Run a deterministic preparation profile (`prop-native-alpha`, `prop-full-alpha-ground`, `portrait-original`, `lpc-sheet-native`) over each verified raw candidate, and write `media-validation.json` beside the run record. |
| `--timeout <seconds>` | Poll deadline for one generation (default 900 image, 1800 audio). |
| `--hosted-budget-usd <n>` | Override the brief's hosted spend ceiling. |
| `--budget-duration <secs>`, `--budget-pixels <n>`, `--budget-retained-bytes <n>` | Override the declared duration/pixel/retained-byte ceilings. |
| `--help` | Print the usage summary. |

`--manifest` may be given relative to the current directory or to the repository
root, so the repo-relative example above works even though the script runs with
`--cwd apps/backend/image`. The other path flags (`--runs-dir`, `--out`) resolve
against the current directory.

Exit codes are distinct on purpose, so a script or an LLM can tell "the brief
says no" from "the runner broke": `0` ok, `1` internal error, `2` blocked plan,
`3` budget refused, `4` invalid invocation, `5` job-state conflict (already
claimed, unknown run).

What a run writes, under `apps/backend/image/src/output/runs/<runId>/`: the run
record (`run.json`), the immutable run lock (`run.lock.json` — the provider
profiles, recipes, declared models and verified reference hashes the run is
bound to), one `jobs/<jobId>.json` per job with its full state history, a
content-addressed `blobs/` store, the namespaced `staged/` copy of each prepared
asset, and `candidates.fragment.json` in the C-518 candidate-record shape. The
shared fragments `staging/manifest.json` and `staging/hashes.json` are merged
under an exclusive lock with atomic replacement, so a killed run can never tear
an earlier fragment. Nothing in the one-job staging root is touched.

Two rules keep the batch recoverable. A submission that times out after the
request left the process is marked `reconciliation_required`, not retried — the
provider may still be computing, and the resource lease is kept until the
provider confirms completion or an operator reconciles it with `--reconcile`.
And a cancellation *request* is reported separately from *confirmed* provider
cancellation: an engine that reports `capabilities.cancel === false` reports
that only polling stopped. Duplicate detection is spec-hash based, so an
identical effective spec reuses its completed job with no second engine call,
while `--variation <n>` always creates a new attempt.

### Versioned workflows and deterministic preparation

Two versioned profiles decide *what* is generated and *how* the bytes are
prepared. Both are data, validated at load time, and both are recorded with the
artifact they produced.

A **workflow profile** pins one engine graph: the model family, the exact weight
filenames it loads, the semantic inputs it accepts and where each one binds, and
the capabilities its graph genuinely proves. Profiles live in
`packages/shared/local-ai/src/lib/workflows/`. `sdxl-legacy` is the shipped
default and keeps the pre-C-520 path available; `flux2-klein-4b-comfyui` is
opt-in and needs its own pinned install; `mystic07-spritesheet-9b` is registered
so its exclusion is auditable but can never be dispatched, and its LoRA can
never be attached to the 4B base. A request that names a capability or a LoRA
the selected profile does not prove is refused before any HTTP submission.

A **preparation profile** pins an ordered, parameterised transformation set of
pixels — alpha extraction and cleanup, a locked resample method, a
content-preserving trim, a lossless encode — plus the QA limits the result is
judged against. Preparation runs on the *verified raw bytes* after they are
durable, so a resumed run prepares the same bytes again instead of
regenerating, and the same input always produces the same prepared SHA-256.
The raw bytes themselves are never rewritten.

`media-validation.json` is the auditable result: the raw and prepared hashes,
the profile id and version, the operation list, every machine finding with its
stable code, and an explicit `manualReviewRequired`. Geometry checks can prove
that an opaque ground plane survived or that a fringe is too wide; they cannot
prove the art is good, and the report says so rather than implying otherwise.

## Recipes are data

Adding a recipe for an existing category/engine is a JSON edit in
`packages/shared/local-ai/src/lib/recipes/recipes.json` — no TypeScript change.
A recipe that names an unknown engine, maps to a category absent from
`ASSET_CATEGORIES`, or asks an engine for something it cannot do (a LoRA on
ComfyUI, say) is rejected at load time with a readable error rather than
silently dropped.

## In-game generation

Generated bytes reach the running game through the registry write seam:

1. `toGeneratedAsset(result, recipe, engine)` derives the shared descriptor —
   content hash, tag, category, `generated:<engine>` provenance.
2. `assetManager.registerGenerated(descriptor, bytes)` verifies the SHA-256,
   writes the bytes to the OPFS/Tauri cache, and inserts an `assets` row plus a
   `local-generated` source at priority `-1` so the local copy always outranks
   a catalog row for the same tag.
3. `assetStore.resolveUrl(tag)` — the synchronous seam the expression resolver
   uses — returns a usable `blob:` URL with **no network access**.

Registration is idempotent by content hash, and a tag already owned by the
catalog is rejected loudly: the boot seed would otherwise silently re-point it
at remote bytes on the next launch.

`PUBLIC_ASSET_GENERATION=false` disables the write seam (the CLI keeps
working for developers). Local sources outrank remote ones, and nothing on this
path requires the network.
