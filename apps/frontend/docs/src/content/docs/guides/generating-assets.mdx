---
title: Generating Assets Locally
description: One engine-agnostic command that turns a prompt into a catalog-ready asset, and how generated bytes become first-class registry assets the game can render.
---

Aikami can generate art with a local engine — no cloud call, no sign-in. The
C-510 pipeline gives you **one command** for it and, for in-game generation,
one write path that makes the result a real registry asset rather than an
in-memory blob.

## One command

```bash
bun run --cwd apps/backend/image generate:asset prop "rusty iron gate"
```

The invocation is `--cwd`-scoped on purpose: the script is declared in
`apps/backend/image/package.json`, so the bare root form
(`bun run generate:asset …`) fails with `Script not found`.

You name a **recipe**, not an engine. The recipe decides the engine, the
prompt template, the negative prompt and the output category:

| Recipe | Category | Output | Tag |
|---|---|---|---|
| `prop` | `props` | `.png` | `props:<slug>` |
| `portrait` | `portraits` | `.webp` | `portraits:<slug>` |
| `expression` | `portraits` | `.webp` | `portraits:<slug>` |
| `tileset` | `tilesets` | `.png` | `tilesets:<slug>.png` |

Useful flags: `--engine sdcpp|comfyui`, `--seed`, `--steps`, `--cfg`,
`--width`, `--height`, `--model`, `--negative`, `--timeout <seconds>`,
`--out`. The slug is the prompt lowercased with every run of
non-alphanumerics collapsed to `-`.

sd-server runs on CPU, so a 512×512/20-step job takes roughly two minutes on a
developer machine and longer under load. `--timeout` is the poll deadline and
defaults to 900s — lower it for a quick smoke test
(`--timeout 120 --steps 4 --width 256 --height 256`), raise it on slow
hardware. A run that hits the deadline exits non-zero and names the deadline it
used.

## What it writes

Into `apps/backend/image/src/output/generated/` (gitignored scratch space):

- the image bytes at their catalog-relative path (`props/rusty-iron-gate.png`),
- `manifest.json` — an `AssetManifest` fragment,
- `hashes.json` — an `AssetHashesFile` fragment (SHA-256 + size),
- `generated_asset.json` — the descriptor, with
  `provenance.source = "generated:<engine>"`.

Repeated runs merge into the existing fragments, so the directory is a
staging area the [catalog publish pipeline](./publishing-catalog-assets.md)
consumes without hand-editing. The CLI exits non-zero on any engine failure
and refuses to report success for an asset whose category the scanner cannot
classify.

## Recipes are data

Adding a recipe for an existing category/engine is a JSON edit in
`packages/shared/local-ai/src/lib/recipes/recipes.json` — no TypeScript change.
A recipe that names an unknown engine, maps to a category absent from
`ASSET_CATEGORIES`, or asks an engine for something it cannot do (a LoRA on
ComfyUI, say) is rejected at load time with a readable error rather than
silently dropped.

## In-game generation

Generated bytes reach the running game through the registry write seam:

1. `toGeneratedAsset(result, recipe, engine)` derives the shared descriptor —
   content hash, tag, category, `generated:<engine>` provenance.
2. `assetManager.registerGenerated(descriptor, bytes)` verifies the SHA-256,
   writes the bytes to the OPFS/Tauri cache, and inserts an `assets` row plus a
   `local-generated` source at priority `-1` so the local copy always outranks
   a catalog row for the same tag.
3. `assetStore.resolveUrl(tag)` — the synchronous seam the expression resolver
   uses — returns a usable `blob:` URL with **no network access**.

Registration is idempotent by content hash, and a tag already owned by the
catalog is rejected loudly: the boot seed would otherwise silently re-point it
at remote bytes on the next launch.

`PUBLIC_ASSET_GENERATION=false` disables the write seam (the CLI keeps
working for developers). Local sources outrank remote ones, and nothing on this
path requires the network.
