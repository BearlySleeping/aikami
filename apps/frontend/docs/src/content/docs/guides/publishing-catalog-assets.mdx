title: Publishing Assets to the Catalog Origin
description: Developer notes on publishing the bundled asset library to the R2 catalog origin — the content-addressed publish pipeline, the attribution gate, and the catalog index.
---

The asset library (LPC sprites, music, sfx, sprites, backgrounds, maps,
tilesets, and content packs) is published to a CDN origin and fetched on
demand. Since the client no longer bundles game data, **this pipeline is what
puts the bytes where the game and the hub can read them** — a publish is a
prerequisite for a working build, not an optional mirror. This page documents
how it works and how to run it.

## What gets published

The pipeline reads the scan outputs in `apps/frontend/client/static/game-data/`:

| File | What it provides |
|---|---|
| `manifest.json` | asset tags, categories, subcategories, paths, extensions |
| `asset_hashes.json` | sha256 + byte size per tag (C-373 sidecar) |
| `asset_credits.json` | attribution per tag, merged by `scan_assets.ts` from three sources |

The three attribution sources:

1. `lpc_credits.json` — per-asset upstream credits joined from the vendored
   LPC generator's `CREDITS.csv` (by the collector, `collect_lpc_assets.ts`).
2. `lpc_credits_supplement.json` — LPC library-level declarations for the
   small set of LPC assets `CREDITS.csv` does not cover (generated by the
   collector).
3. `project_licenses.json` — the committed project-owned declaration for
   non-LPC assets (`scripts/src/lib/catalog/`).

The pipeline scans two roots: `static/game-data/` and the content-pack
sources. Maps, tilesets, and content packs are full catalog categories — the
earlier "dev-only sandbox files" exclusion was removed once the client began
resolving them through the registry.

Alongside the content-addressed assets, the pipeline publishes a small set of
mutable **seed files** under `seed/` — the compact boot seed, the offline-core
declaration, credits, and audio metadata. The client fetches these at boot to
build its local asset registry.

## Running a publish

```bash
# credentials + origin live in scripts/.env.production (see scripts/.env.example)
bun run scripts/src/lib/catalog/publish.ts --mode production
```

The run is:

1. **Attribution preflight** — a hard gate *before* any upload. Every catalog
   tag must resolve to one of the three attribution sources, with non-empty
   `licenses` and `authors`. There is **no bypass flag**. A violation aborts
   with zero bytes written and every unresolved tag named.
2. **Content-addressed upload** — objects go to
   `assets/<sha256[0:2]>/<sha256>.<ext>` with the correct MIME type and
   `Cache-Control: public, max-age=31536000, immutable`. The bucket is listed
   once and existing keys are skipped, so re-runs are cheap and interrupted
   runs resume.
3. **Index publication (last)** — `index/v1/catalog.json` (category summaries
   only) plus one shard per category, written only after every referenced
   object is confirmed uploaded, with a 60-second cache.

Environment (`scripts/.env.*`, fetched from Secret Manager by
`download_secrets.ts`):

```
CLOUD_FLARE_CATALOG_BUCKET_ACCESS_KEY_ID
CLOUD_FLARE_CATALOG_BUCKET_SECRET_ACCESS_KEY
CLOUD_FLARE_CATALOG_BUCKET_ENDPOINT
CATALOG_ORIGIN_URL   # public origin, injected — never hardcoded
CATALOG_BUCKET       # optional, defaults to aikami-catalog
```

These credentials belong to the publish pipeline alone. The hub never writes to
R2, so they must never appear in the hub's environment.

## Regenerating attribution sidecars

The sidecars are committed, so a publish needs no vendored generator. To
regenerate them (after adding LPC assets):

```bash
# requires the vendored generator (examples/Universal-LPC-Spritesheet-Character-Generator)
bun run scripts/src/lib/ops/collect_lpc_assets.ts      # catalog + lpc_credits.json + supplement
bun run scripts/src/lib/ops/scan_assets.ts             # manifest + hashes + merged asset_credits.json
```

## The origin

- Bucket: `aikami-catalog` (Cloudflare R2, WEUR, Standard storage class)
- Public origin: `https://assets.bearlysleeping.com` (custom domain, no credentials on reads)
- Objects are immutable; "updating" an asset publishes a new object and a new
  index entry. Rollback is publishing an older index.

### CORS (required before promotion past sandbox)

The hub consumes the index from the browser, so the bucket must permit
cross-origin reads from the hub's origins. The publish pipeline's S3
credentials cannot set a CORS rule (`PutBucketCors` is denied), so this is a
maintainer action in the Cloudflare R2 dashboard — apply it to
`aikami-catalog`:

- Allowed origins: `https://hub.bearlysleeping.com`,
  `https://hub.stg.bearlysleeping.com`, `https://aikami.bearlysleeping.com`
- Allowed methods: `GET`, `HEAD`
- Allowed headers: `*`

**Promotion beyond sandbox must be blocked until this CORS configuration is
complete.** Without it, a browser fetch of the index fails the preflight and
C-396's browse feature cannot ship — this is the AC-3 gate.

## Adding a new non-LPC asset

Add its tag to `scripts/src/lib/catalog/project_licenses.json` with explicit
`licenses`, `authors` and `sourceUrls` — that file is the review surface.
The publish preflight will refuse the tag until it is declared.
